# 局内动态任务系统规划

> **更新日期**：2026-08-13
> **状态**：核心规则已确认，奖励持续时间等少量细节仍可调
> **关联文档**：`Docs/boss-extraction-shop-dynamic-tasks.md`、`Docs/extraction-shop-implementation-plan.md`

## 一、已确认的核心规则

1. 第 5、10、15、20、25 波为 Boss 波。
2. 每个 Boss 前固定出现一次任务，任务波次为第 3、8、13、18、23 波。
3. 任务在目标波后半段出现，推荐为该波开始后 35～45 秒。
4. 任务信标存在接取时间限制；超时未接取视为放弃，不算任务失败。
5. 玩家进入任务信标并持续停留 1 秒后接取任务。
6. 同一时间最多存在一个任务。
7. 任务暂定三类：守护固定区域、运送任务、悬赏讨伐。
8. 守护任务离开区域后有短暂返回宽限，宽限耗尽才失败。
9. 运送任务中加入少量任务专属拦截敌人。
10. 任务完成后的奖励候选从武器升级、强力属性成长和正向祝福中随机生成。
11. 未接取或接取后失败均不直接惩罚玩家，只失去本次任务奖励。

## 二、时间与章节节奏

当前实现每波持续 90 秒，因此第一个 Boss 阶段的时间轴为：

| 波次 | 理论时间 | 内容 |
|------|----------|------|
| 第 1 波 | 0:00～1:30 | 开局适应 |
| 第 2 波 | 1:30～3:00 | 普通战斗 |
| 第 3 波 | 3:00～4:30 | 约 3:35～3:45 出现任务信标 |
| 第 4 波 | 4:30～6:00 | Boss 前准备 |
| 第 5 波 | 6:00 开始 | Boss 战 |

本文按“第 5 波是 Boss 波”理解。任务约在 3:40 出现，完成后仍留有一段普通战斗时间消化奖励，再进入 Boss。

后续阶段不能按全局 `game.elapsed` 的绝对分钟数触发，因为 Boss 超时、选卡、撤离抉择都会暂停或改变实际节奏。任务应按波次号与波内时间触发：

```text
任务波次 = 下一个 Boss 波次 - 2
波内已进行时间 = CONFIG.waves.duration - waveDirector.timeRemaining
触发区间 = 35～45 秒
```

任务波次固定为：

```text
3、8、13、18、23
```

### 推荐时间参数

```text
任务出现：目标波开始后 35～45 秒
接取窗口：12 秒
接取蓄力：在信标内连续停留 1 秒
结果提示：2.5 秒
任务最晚结束：下一 Boss 波开始前
```

35～45 秒的轻微随机能够保留“第三波后半段”的稳定预期，同时避免每局都在完全相同的一秒出现。

## 三、任务总体流程

```text
阶段开始
→ 预选任务类型和触发时间
→ 进入第 3/8/13/18/23 波
→ 到达波内触发时间
→ 生成任务信标，进入 offered
→ 玩家停留 1 秒：进入 active
→ 接取倒计时耗尽：进入 expired
→ active 任务完成：进入 succeeded，打开任务奖励选择
→ active 任务违反条件或超时：进入 failed
→ 清理任务实体，等待下一个 Boss 阶段
```

### 未接取与失败必须分开

- `expired`：玩家没有接取，属于主动放弃。
- `failed`：玩家接取后没有完成。
- `succeeded`：完成并获得奖励。

结算统计建议分别记录：

```js
{
  offered: 0,
  accepted: 0,
  completed: 0,
  failed: 0,
  ignored: 0,
}
```

## 四、任务接取信标

### 生成位置

- 信标生成在玩家约 300～440px 外。
- 不生成在玩家脚下。
- 生成时应处于当前视野内或接近视野边缘。
- 信标和普通拾取物使用不同颜色与轮廓。
- 信标位置不跟随玩家移动。

### 接取方式

玩家进入信标范围后开始累计 1 秒接取进度：

- 离开信标，接取进度快速回退或清零。
- 达到 1 秒后只触发一次接取。
- 接取过程中显示环形进度。
- 信标剩余时间少于 3 秒时变为红色闪烁。

推荐信标半径为 55～65px，避免玩家必须精确踩点。

### 接取 HUD

```text
可选任务 · 紧急运送
进入信标停留 1 秒接取
剩余 8.4s
奖励：强力成长三选一
```

## 五、任务一：守护固定区域

### 核心目标

玩家接取后必须持续留在指定区域中战斗固定时长。离开区域会进入短暂警告，未及时返回则任务失败。

### 流程

1. 任务信标本身转化为守护区域。
2. 玩家接取时已经位于区域内，守护进度立即开始。
3. 玩家处于区域内时累计连续守护时间。
4. 玩家离开时暂停守护进度并启动离场宽限。
5. 宽限内返回，守护继续。
6. 宽限耗尽，任务立即失败。
7. 达到所需守护时间，任务完成。

### 推荐参数

| 任务阶位 | 守护时长 | 区域半径 | 离场宽限 |
|----------|----------|----------|----------|
| T1 | 18s | 130px | 1.0s |
| T2 | 20s | 125px | 1.0s |
| T3 | 22s | 120px | 0.9s |
| T4 | 24s | 115px | 0.9s |
| T5 | 26s | 110px | 0.8s |

首版不需要额外生成守护专属敌人，普通波次已经提供持续压力。后续若任务过于简单，可以在区域边缘生成少量定向攻击者。

### 重要规则

- 守护进度是连续进度，不是可无限累计的进度。
- 离开后在宽限期内返回，不重置已经完成的守护时间。
- 宽限期耗尽才失败，避免边缘抖动或短暂闪避造成即时失败。
- 选卡界面或 Debug 暂停时，守护与离场计时都暂停。

### HUD 示例

```text
守护仪式  14.8 / 22.0s
不要离开守护区域
```

离场后：

```text
正在离开任务区域！
0.7s 内返回
```

## 六、任务二：紧急运送

### 核心目标

玩家从接取点 A 携带任务物品，在规定时间内抵达交付点 B。途中会出现少量任务专属拦截敌人。

### 流程

1. 玩家在 A 点完成 1 秒接取。
2. 接取后获得任务物品，A 点消失。
3. 系统根据玩家位置生成 B 点和屏外方向箭头。
4. 玩家向 B 点移动，任务系统周期性生成少量拦截敌人。
5. 玩家进入 B 点范围后自动交付并完成任务。
6. 运送倒计时耗尽，任务失败并清除任务物品、B 点与残留拦截敌人。

### 推荐参数

| 任务阶位 | A-B 距离 | 时限 | 每批拦截敌人 | 批次间隔 |
|----------|----------|------|----------------|----------|
| T1 | 1500～1750px | 22s | 1～2 | 6s |
| T2 | 1600～1850px | 22s | 2 | 5.5s |
| T3 | 1700～1950px | 21s | 2 | 5s |
| T4 | 1800～2050px | 21s | 2～3 | 4.5s |
| T5 | 1900～2200px | 20s | 3 | 4s |

距离需要在浏览器实测后调优。目标是让纯直线移动占用约一半时限，其余时间用于绕开或处理敌人。

### 拦截敌人规则

- 优先生成在玩家前方或路线侧前方约 280～420px。
- 不直接生成在玩家碰撞范围内。
- 根据任务阶位使用 `chaser`、`enhancedChaser`、`charger` 等现有类型。
- 不使用 Boss 或高血量 `shield` 阻挡低阶任务。
- 不计入 `WaveDirector.quota`，不能阻止普通波推进。
- 建议标记为任务敌人，并禁止稀有物品掉落，避免玩家利用任务反复获取额外精英奖励。
- 可以正常计入击杀数；是否掉经验宝石可在平衡阶段决定，首版建议少量正常掉落。
- 任务结束后仍存活的拦截敌人可以转为普通敌人，或在短暂消散效果后清除；推荐清除，避免任务失败继续留下额外压力。

### 运送公平性

- 首版不采用“受到一次伤害就失败”。
- 首版不采用过高的携带减速。
- 如实测过于简单，可增加 5%～10% 的轻微携带减速，但不建议一开始就启用。
- B 点方向随机，但不能生成得过近或出现异常短路线。
- 屏外必须持续显示方向和距离。

### HUD 示例

```text
紧急运送  15.2s
目标距离 1260px
```

## 七、任务三：悬赏讨伐

### 核心目标

玩家接取后，在时限内击杀一只被任务标记的强化敌人。这一任务主要检验玩家当前构筑的输出能力。

### 流程

1. 玩家在信标处接取悬赏。
2. 在玩家约 450～650px 外生成悬赏目标。
3. 目标拥有独立标记、特殊描边和屏外方向箭头。
4. 任何武器、召唤物或 DoT 通过统一 `_killEnemy()` 击杀目标都算完成。
5. 超时后任务失败，悬赏目标清除，不掉落任务奖励。

### 推荐参数

| 任务阶位 | 目标类型建议 | 额外生命倍率 | 伤害倍率 | 时限 |
|----------|--------------|--------------|----------|------|
| T1 | enhancedChaser | ×2.5 | ×1.10 | 40s |
| T2 | charger / enhancedChaser | ×3.0 | ×1.15 | 40s |
| T3 | charger / shield | ×3.5 | ×1.20 | 38s |
| T4 | shield / charger | ×4.0 | ×1.25 | 38s |
| T5 | 强化 shield / charger | ×4.5 | ×1.30 | 36s |

生命倍率作用在敌人完成当前波次缩放后的数值上，不能重复应用波次成长。

### 目标规则

```js
enemy.taskId = task.id;
enemy.taskRole = 'bountyTarget';
enemy.suppressRankReward = true;
enemy.suppressRareDrop = true;
```

- 不建议把悬赏目标直接标记为 `rank === 'boss'`，否则可能误触发 Boss 统计或撤离逻辑。
- 可以使用 `rank === 'elite'` 的血条表现，但必须禁止自动精英稀有掉落。
- 目标速度不要大幅强化，“追不上”不应成为主要难度。
- 任务失败后目标不得继续作为免费精英奖励留在场上。

### HUD 示例

```text
悬赏讨伐  27.6s
目标生命 63%
```

## 八、任务类型调度

每个 Boss 阶段只安排一种任务。推荐规则：

- 三种任务默认等权随机。
- 任务类型不与上一次重复；若抽到上一次类型，则从剩余两类重新抽取。
- 第一个阶段也随机，不固定教学任务；如果后续需要教学，可将第一局首次任务固定为守护区域。
- RNG 允许注入，确保 smoke 测试可复现。

```js
const TASK_TYPES = ['guard', 'delivery', 'bounty'];
```

## 九、任务奖励系统

### 奖励定位

任务奖励应当让玩家在进入下一场 Boss 前明显变强，而不是只获得少量经验或治疗。因此首版采用独立的“任务奖励三选一”，不直接复用普通升级卡的单层强度。

任务完成后：

1. 当前世界暂停。
2. 打开任务奖励三选一界面。
3. 玩家选择一项奖励。
4. 奖励立即生效。
5. 返回战斗，继续向下一场 Boss 推进。

本文建议所有任务奖励持续到**本局结束**。这样任务构成局内构筑的一部分，也符合卡牌成长和武器升级的预期。

### 三类奖励

#### A. 武器升级

- 从玩家已经拥有且未满级的武器中选择一把，提升 1 级。
- 奖励卡上必须明确显示具体武器和升级后的等级。
- 武器已满级时不得生成该武器的升级奖励。
- 所有武器满级时，武器升级槽替换为强力属性或祝福。

示例：

```text
剑气强化
剑 Lv3 → Lv4
```

#### B. 强力属性成长

单次任务属性奖励建议约等于普通属性卡的 2 层，并单独记录，不占普通 `attrMaxStack` 上限。

| 奖励 | 建议效果 |
|------|----------|
| 强攻 | 伤害 +30% |
| 铁壁 | 护甲 +30 |
| 聚灵 | 拾取范围 +100px |
| 悟道 | 经验倍率 +30% |
| 血契 | 最大生命 +40，并恢复 40 |
| 疾风 | 移速 +12% |

建议通过 `taskBonuses` 应用，不直接向 `attrStacks` 连续添加两层，避免占用普通升级卡的叠加上限。

#### C. 正向祝福

祝福是由两项效果组成的特殊局内 Buff，强度高于普通单项属性卡。

首版可以从实现成本较低的组合开始：

| 祝福 | 建议效果 |
|------|----------|
| 猎杀祝福 | 对精英和 Boss 伤害 +25% |
| 坚韧祝福 | 最大生命 +25、护甲 +20，并恢复 25 |
| 疾猎祝福 | 移速 +10%、拾取范围 +80px |
| 灵悟祝福 | 经验倍率 +25%、伤害 +10% |
| 战意祝福 | 伤害 +20%、移速 +6% |

后续可以扩展为更有机制感的祝福，例如低血量增伤、击杀恢复或一次致死保护，但首版优先使用现有属性体系能稳定支持的效果。

### 随机奖励生成规则

任务奖励不固定保证某一类别，而是从统一奖励池中随机生成三张不同的候选卡，玩家再从中选择一张。

统一奖励池包含：

```text
具体武器升级
强力属性成长
正向祝福
```

首版推荐基础权重：

| 奖励类别 | 基础权重 |
|----------|----------|
| 武器升级 | 40% |
| 强力属性 | 35% |
| 正向祝福 | 25% |

生成流程：

1. 收集当前有效奖励，移除满级武器、已达到唯一上限的祝福和其他无效选项。
2. 按类别权重随机抽取奖励。
3. 同一组三张候选不可完全重复。
4. 抽到无有效选项的类别时，重新归一化剩余类别权重。
5. 依次抽取，直到得到三张有效奖励；奖励池不足三张时展示全部有效奖励。

因此可能出现：

```text
2 张武器升级 + 1 张祝福
1 张武器升级 + 2 张强力属性
3 张不同的正向成长
```

奖励随机不等于奖励强度失控：所有候选都必须达到任务奖励的最低强度标准，不能混入普通单层属性卡或纯治疗等明显偏弱选项。

任务阶位暂时不改变奖励权重。收集完成率和选择率后，再考虑让高阶任务提高正向祝福或高级奖励的出现概率。

随机函数必须允许注入 `rng`，以便 smoke 测试稳定覆盖固定抽取结果。
### 奖励队列

任务完成可能与正常升级选择发生在同一帧，因此不能简单覆盖 `currentOffers`。建议增加任务奖励队列：

```js
pendingTaskRewards.push({ taskType, tier });
```

处理优先级建议：

```text
已经打开的选择界面
→ 待处理任务奖励
→ 普通升级选择
→ 返回战斗
```

任务奖励仍可复用现有选卡 UI，但设置：

```js
choiceOrigin = 'task';
currentOffers = generateTaskRewardOffers(game, rewardContext);
```

`_finishChoice()` 必须区分 `task` 和 `levelup`，任务奖励不能错误减少 `pendingChoices`。

## 十、任务状态与数据结构

### `CONFIG.tasks`

```js
tasks: {
  enabled: true,
  triggerWaves: [3, 8, 13, 18, 23],
  triggerDelay: [35, 45],
  offerDuration: 12,
  acceptHoldDuration: 1,
  beaconRadius: 60,
  beaconDistance: [300, 440],
  resultDuration: 2.5,
  guard: { /* 守护参数 */ },
  delivery: { /* 距离、时限、拦截参数 */ },
  bounty: { /* 目标倍率和时限 */ },
  rewards: { /* 类别权重、强力属性与祝福参数 */ },
},
```

### `TaskDirector`

```js
{
  state: 'active',
  id: 3,
  type: 'delivery',
  tier: 2,
  wave: 8,
  triggerAt: 39.2,
  offerRemaining: 0,
  acceptProgress: 1,
  timeRemaining: 16.5,
  progress: 0,
  progressMax: 1,
  targetPosition: { x, y },
  payload: {},
  resultMessage: null,
}
```

任务专属字段放入 `payload`：

```js
// 守护
payload: {
  center: { x, y },
  radius: 120,
  holdProgress: 8.4,
  leaveGraceRemaining: 0.9,
}

// 运送
payload: {
  destination: { x, y },
  nextInterceptorAt: 4.5,
  interceptorIds: [],
}

// 悬赏
payload: {
  targetEnemyId: 42,
}
```

敌人需要稳定的运行时 ID，不能依赖 `enemies` 数组索引，因为死亡敌人会在每帧被过滤。

## 十一、代码接入方案

### 新增文件

- `js/systems/tasks.js`
  - `TaskDirector`
  - 调度、信标、接取、任务更新、结果和清理
- `js/task-rewards.js`
  - 任务奖励定义
  - `generateTaskRewardOffers()`
  - 强力属性、祝福与武器升级应用

首版也可以先把任务定义放在 `js/systems/tasks.js` 中，超过约 350 行后再拆分。

### 修改 `js/game.js`

1. `reset()` 中创建任务导演、任务统计、任务奖励队列和 `taskBonuses`。
2. `update()` 中在玩家和摄像机更新后调用任务导演。
3. `_killEnemy()` 中通知任务系统，并支持任务敌人的掉落抑制。
4. `recomputeMods()` 中叠加任务属性与祝福。
5. `onBossWaveCleared()`、`_onDeath()` 和 `reset()` 中清理任务实体。
6. `render()` 的世界坐标阶段绘制信标、守护区域、交付点和目标标记。
7. 选卡流程支持 `choiceOrigin === 'task'`。
8. `_finishRun()` 加入任务统计。

### 修改 `js/systems/waves.js`

- `startWave()` 后调用 `taskDirector.onWaveStarted()`。
- 波次导演只发布波次变化，不承载具体任务逻辑。
- Boss 波开始时执行任务安全检查，确保任务不会残留进入 Boss 战。

### 修改 `js/hud.js`

- 右上角状态区下方增加任务面板。
- offered 阶段显示接取倒计时。
- active 阶段显示目标、进度、时间和距离。
- 世界目标在屏外时绘制边缘方向箭头。
- 任务奖励界面标题与普通升级明确区分。

## 十二、失败与清理规则

### 通用失败

- 玩家死亡：本局结束，任务自动清理。
- 进入 Boss 波时任务仍未结束：任务失败并清理；正常参数下不应频繁发生。
- 目标实体异常丢失：任务失败，不能卡死状态机。

### 无惩罚原则

- 未接取：没有奖励，也没有惩罚。
- 接取后失败：没有奖励，也不扣血、不扣属性、不生成额外永久敌人。
- 任务失败后的专属拦截者和悬赏目标必须清理。

### 防止重复结算

每个任务必须有唯一 ID，并在成功时设置终态后再发奖励：

```text
检查完成条件
→ state = succeeded
→ 入队一次奖励
→ 禁止再次处理完成事件
```

## 十三、测试规划

每次实现任务系统后运行 `npm run smoke`，并扩展 `tools/headless-smoke.mjs`。

### 调度

- 任务只在 3、8、13、18、23 波出现。
- 触发时间位于波内 35～45 秒。
- Boss 波和其他普通波不生成任务。
- 每个 Boss 阶段最多一个任务。
- 不连续生成同一种任务。

### 接取

- 玩家在信标外不累计接取。
- 停留不足 1 秒不会接取。
- 达到 1 秒后只接取一次。
- 12 秒未接取进入 `expired`，不增加失败数。

### 守护

- 玩家在区域内累计连续守护时间。
- 离开后启动宽限警告。
- 宽限内返回不会失败。
- 宽限耗尽立即失败。
- 达到守护时长只奖励一次。

### 运送

- B 点距离处于配置范围。
- 到达 B 点后完成。
- 超时失败。
- 拦截敌人按间隔生成且不计入波次 quota。
- 任务结束后清理任务物品、B 点和拦截敌人。

### 悬赏

- 只有带匹配任务 ID 的目标死亡才完成。
- 普通敌人死亡不推进任务。
- DoT、召唤物和武器击杀都能完成。
- 失败后目标不掉任务或普通精英奖励。

### 奖励

- 完成任务从统一奖励池随机生成最多三张有效奖励。
- 有可升级武器时，武器升级按配置权重参与随机，但不保证每次出现。
- 任务奖励不会覆盖普通升级选择。
- 武器升级正确改变等级并刷新联动。
- 强力属性不占普通属性卡上限。
- 同名不可叠加祝福不会重复出现。
- 失败和忽略不产生奖励。

随机调度、任务类型、生成位置和奖励生成都应允许注入 RNG，测试不得依赖真实随机序列。

## 十五、验收标准

- 第 3、8、13、18、23 波后半段各有一次任务机会。
- 玩家可以忽略任务，接取信标会在 12 秒后消失。
- 接取必须在信标内停留 1 秒。
- 守护、运送和悬赏分别考验站位、移动和输出。
- 守护任务提供约 1 秒离场宽限。
- 运送任务存在少量拦截敌人，并能安全清理。
- 任务完成后稳定进入随机强力奖励三选一。
- 奖励候选从武器升级、强力属性和正向祝福统一池中随机生成。
- 任务失败没有直接惩罚，也不会留下任务实体。
- 任务不得阻塞普通波推进或误触发 Boss 撤离逻辑。
- 新增 smoke 测试确定性通过，原有测试全部通过。
