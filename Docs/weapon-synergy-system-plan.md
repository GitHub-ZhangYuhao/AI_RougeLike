# 武器联动系统规划

> **2026-08-19 复核注记**：本文档为原型期联动规划。Godot 版已简化为「单一主联动」（仅一件主武器决定联动对象），裁决见 `GameProject/RULES.md` 附录 B #11；联动事宜以 RULES.md 为准。

> 状态：已确认设计 / 实现与验收依据
> 日期：2026-08-13
> 适用版本：当前 6 武器、3 武器槽、武器最高 Lv6 的浏览器版本
> 玩法来源：Notion「武器联动思维导图（2026-08-12）」与本地实现复核结论

## 1. 目标与范围

- 系统仅保留双武器联动，完整覆盖 6 把武器的 **15 组两两组合**。
- 任意两把已持有武器均达到 **Lv4** 后，对应联动自动激活。
- 即使持有三把武器，也只按双武器对独立计算；不产生额外三武器共鸣或组合效果。
- 玩家可点击现有武器框，手动选择并锁定一组 Build；取消选择后恢复自动模式。
- 联动优先改变攻击路径、目标选择、状态、场地或资源循环，不退化为单纯数值加成。
- 联动伤害、击杀和状态必须经过统一战斗入口，并遵守 Boss 修正、掉落与击杀统计。
- 高频联动必须具备冷却、数量上限、动作去重或递归保护。
- **全部 15 个联动必须拥有独立、可辨识的战斗特效。**

## 2. 激活与手动 Build 规则

### 2.1 自动激活

1. 玩家同时持有对应两把武器。
2. 两把武器均达到 Lv4。
3. 对应联动立即激活，不进入普通升级候选。
4. 联动本身不单独升级，强度随基础武器等级和数值成长。
5. 持有三把武器时，各双武器对独立判定；没有额外三武器机制。

### 2.2 手动锁定

1. 未锁定两把武器时使用自动模式，所有满足条件的联动均可激活。
2. 点击第一把武器框进入待选状态，此时仍保持自动模式。
3. 点击第二把武器框后锁定对应 Build；锁定期间只允许该组合的联动激活。
4. 锁定后点击第三把武器时，保留第一个选择并替换第二个选择。
5. 再次点击已选武器可取消选择；不足两把时立即解除锁定并恢复自动模式。
6. 锁定组合未达到 Lv4 时显示未激活提示，不得回退到其他组合。

| 14 | 炽热披风 × 死灵法杖 | **鬼火护卫** | 仆从进入披风后获得周期火伤光环，离开后短暂保留。多个光环对同一目标共享或限制触发频率。 | 仆从周围出现鬼火环与飘动火点，伤害结算时鬼火向目标扑击。 |

## 4. 特效统一要求

1. 每个联动必须有独立的触发前兆、触发主体或结果反馈，不能只复用基础武器粒子并改色。
2. 玩家应能在三组联动同时激活时，仅凭画面判断是哪一组联动被触发。
3. 特效生命周期必须与实际判定同步；场地、蓄能、标记、中继和失活状态不能残留错误视觉。
4. 高频联动使用轻量特效并设置实例上限；低频联动可使用更强轮廓、闪光或震屏，但不得遮挡敌人和危险提示。
5. 联动生成物和特效必须在暂停、死亡、重开、返回菜单及 Build 失活时正确清理。
6. 特效实现属于 Build 完成条件；只有数值或伤害逻辑、没有可辨识特效的联动不算完成。

## 5. 技术约束

### 5.1 联动定义与稳定 ID

- 联动定义集中维护武器组合、Lv4 条件、名称和实现状态。
- `weaponIds` 必须标准化，组合结果与持有顺序无关。
- 运行时状态按联动 ID 保存冷却、标记、一次性触发记录和场地引用。
- **“雷剑引雷”仅修改显示名和行为，ID 必须继续使用 `sword-talisman-mark`，避免存档、测试和代码迁移。**
- 获得或升级武器后重新计算激活集合；重开时清空运行时状态。

### 5.2 统一来源与递归保护

所有可触发联动的命中应携带来源元数据：

```js
{
  sourceWeaponId: 'lightning-talisman',
  sourceAction: 'lightning-strike',
  sourceTags: ['lightning', 'direct'],
  synergyId: null,
  noSynergy: false,
  noSummon: false,
}
```

- `sourceWeaponId` 标识基础武器来源。
- `sourceAction` 区分近战、飞剑、拔剑斩、引雷、闪电链、炉火、仆从攻击和自爆等动作。
- `synergyId` 标识联动来源。
- `noSynergy` 阻止联动伤害继续触发联动。
- `noSummon` 阻止联动击杀继续产生仆从。
- 单次动作对同一目标、场地或中继节点使用稳定 ID 去重。

### 5.3 统一事件入口

联动系统需要受控接收：

- 武器获得、升级和 Build 锁定变化。
- 命中、弹道路径、弹射路径和伤害结果。
- 场地创建、更新、重叠和销毁。
- 仆从创建、选敌、到期、自爆、槽位缩减、上限替换及其他消亡事件。
- 特殊动作，例如拔剑斩、引雷和开炉。

仆从的所有移除方式必须进入统一消亡结算，确保尸火炼丹不会遗漏槽位缩减或上限替换。

## 6. UI 与战斗反馈

- HUD 显示当前自动激活或手动锁定的 Build。
- 武器框显示第一、第二选择顺序、锁定边框和 Lv4 条件。
- Build 名称统一显示“雷剑引雷”，不得显示废弃名称。
- 联动触发时优先通过独立特效反馈；必要时补充短文本，不长期占用屏幕。
- 调试模式应能显示联动 ID、触发次数、冷却、实例数和递归阻止次数。

## 7. 状态反应边界

状态反应作为后续独立设计项，当前文档不定义其组合规则、伤害公式或实现状态。

- 灼烧、流血、尸毒、感电、冻结等名称仅作为后续设计候选。
- 基础武器已有的灼烧、流血、毒、减速或冻结效果，不等同于状态反应系统已经实现。
- 状态反应不得混入本轮 15 个双武器联动的完成度统计与验收。

## 9. 测试计划

### 9.1 基础设施与选择

1. 15 个定义完整覆盖全部两两组合，无重复、无缺失。
2. 组合键与武器持有顺序无关。
3. 任意一把武器未达到 Lv4 时联动不激活；双方达到 Lv4 后自动激活。
4. 持有三把 Lv4 武器时仅激活三组双武器联动，不产生额外三武器机制。
5. 点击两把武器后只激活锁定 Build；取消任一选择后恢复自动模式。
6. 重开、返回菜单和重新开局清空全部联动运行时状态及特效。
7. “雷剑引雷”的名称已更新，但 ID 仍为 `sword-talisman-mark`。

### 9.2 关键行为回归

- **雷剑引雷**：分别验证近战斩击、主飞剑、拔剑斩和剑意飞剑的每次有效命中都会立即产生一次联动落雷；验证联动落雷不递归触发；验证不存在废弃目标状态。
- **焚刃**：验证近战和拔剑斩使用正确方向释放短程火刃，命中范围、穿透、冷却和 `noSynergy` 正确。
- **尸雷跳板**：验证不同等级、不同来源的所有存活死灵仆从均可中继；仆从不受伤且不消耗敌人弹射次数。
- **尸火炼丹**：分别验证到期、自爆、槽位缩减和上限替换；每个仆从只转化一次，炉火进度受上限约束。
- **其余 11 个 Build**：继续验证原有触发条件、冷却、数量上限、状态清理和递归保护。

### 9.3 特效验收

1. 为 15 个联动逐项截取或观察触发画面，确认特效与第 3 节一致。
2. 多组双武器联动同时激活时，在密集敌群中仍能辨认触发来源。
3. 高频触发、多炉火场、多玉环和多仆从场景下无明显实例堆积或帧率异常。
4. 暂停、死亡、重开、返回菜单、取消 Build 和切换 Build 后无残留特效。
5. 特效不遮挡敌人、Boss 危险提示、拾取物和 HUD。

### 9.4 命令与浏览器验证

- 运行 `npm run smoke`，扩展 `tools/headless-smoke.mjs` 覆盖上述确定性行为。
- 运行 `npm start`，验证鼠标选择、HUD、多组双武器联动并发、全部独立特效、暂停、死亡和重开。

## 10. 当前决策摘要

- 仅实现完整 15 组双武器联动，不实现三武器共鸣。
- 联动默认在双方 Lv4 时自动激活，也可点击武器框手动锁定一组 Build。
- Build 名称统一为“雷剑引雷”，保留 ID `sword-talisman-mark`；所有道剑攻击命中直接触发联动落雷，不再使用目标标记流程。
- 尸雷跳板允许所有存活死灵仆从中继，不限定特定等级或尸体类型。
- 焚刃使用沿斩击方向的短程定向火刃。
- 尸火炼丹覆盖所有仆从消亡路径。
- 状态反应留作后续独立设计，不计入当前实现完成度。
- 全部 15 个联动必须具有独立可辨识特效，否则不算完成。
